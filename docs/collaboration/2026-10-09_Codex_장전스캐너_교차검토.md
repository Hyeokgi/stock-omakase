## R1. 하루 최초 적재 제한과 증거 복구를 분리해야 한다

근거는 `omakase.py:3442`, `3451`, `3494`, `3532`, `3563`이다.

현재는 원장에 오늘 스캐너 채널 행이 하나라도 있으면 모든 추가 진입을 막는다. feature_store·rank_pool·scanner 영수증도 `if new_rows:` 안에 있어 새 행이 없으면 실행되지 않는다.

다음 실패를 가짜 시트로 재현했다.

1. 실제 `append_rows` 문장을 실행하되 가짜 서버는 행을 저장한 후 TimeoutError를 반환한다.
2. 원장에는 오늘 행이 남지만 append 다음의 후보·영수증 보존에는 도달하지 않는다.
3. 다음 회차에서 실제 `scanner_entries_today`가 1을 반환하고 실제 `add_channel`은 즉시 반환한다.
4. `new_rows=[]`인 상태로 원문의 `if new_rows:` 블록을 실행하면 증거 저장 전체가 생략된다.

최초 원장 적재 뒤 로컬 파일 저장/원격 커밋만 실패한 경우도 같은 복구 공백이 있다. 이는 단순히 다음 회차에 다시 선정하면 해결되는 문제가 아니다. 그 방법은 시점이 다른 후보 풀을 섞는다.

권고는 **후보 선정 잠금**과 **원장·증거 저장 완료**를 분리하는 것이다.

- 최초 후보와 당시 입력·run ID·시각을 영속 보존한 뒤 해당 묶음으로 적재한다.
- 원장 재조회로 저장 여부를 확정하고, 다음 회차는 같은 묶음의 누락된 저장만 복구한다. 새 후보를 보충하지 않는다.
- 최초 입력을 확보하지 못하면 복구 불가/결측으로 남긴다. 나중 입력을 최초 입력인 것처럼 쓰거나 PASS로 보정하지 않는다.
- 원장 적재 자체가 전혀 안 됐으면 현 구현은 후속 회차 적재를 허용한다. 그런데 창은 여전히 15:00~15:29이므로 첫 성공이 늦어질 수 있다. '첫 적재 1회'는 '15:05 이전 관측 보장'이 아니다. 실제 관측·사용 가능·저장 시각을 구분해야 한다.
- 리포트 행만 존재할 때 스캐너 최초 적재를 허용하는 동작은 기존 시험과 소스 대조에서 이상 없었다.

하루 단위 잠금은 같은 날 다른 풀을 섞지 않는다는 점에서 채널 단위 잠금보다 목적에 맞는다. 다만 사용자에게 설명했던 범위보다 넓고 실패 복구가 별도이므로 이 두 사항을 함께 승인받아야 한다.

## R2. 시간외 보존용 읽기가 실패하면 원래 기록을 지운다

근거는 `omakase.py:2854`와 `2867`의 예외 처리, 이후 helper_sheet 전체 갱신이다.

기존 AA~AC 조회가 TimeoutError를 던지도록 실제 보존 블록을 실행했다. 예외는 경고로 끝나고 `results`에는 새 결측 문자열이 그대로 남았다. 이후 전체 시트 갱신은 계속된다. 이전 저녁 값이 시트에 있었다면 이 경로가 이를 결측으로 덮는다. 다음 아침 회차도 이미 지운 값을 복구할 수 없다.

권고는 읽기 실패 시 **이전 관측을 훼손하는 갱신을 생략하고 별도 상태를 남기는 것**이다. 다른 수집은 계속할 수 있다. 단, 행 순서가 바뀌는 시트에서 AA~AC만 단순 제외하면 종목과 값이 어긋날 수 있으므로 코드 기준 매핑을 보장하거나 해당 보조 시트의 전체 갱신을 그 회차만 보류하는 방식으로 구현해야 한다.

추가 확인 사항은 다음과 같다.

- 장전은 AA·AB를 개별 날짜 검증하지만 보존 여부는 AA만으로 정한다. AA 결측·AB 유효인 야간 자료도 다룰 계획이면 열별 보존 시험이 필요하다. 현재 실제 그런 자료가 있는지는 미확인이다.
- AC는 이력 전용 필드가 아니다. `omakase.py:2947`에서 DB_스캐너 시장 표시에 재사용된다. 전날 AA·AB와 같은 출처 라벨을 붙이는 취지는 이해하지만 현재가의 시장과 전날 관측의 시장을 구분하는지 소비자별 확인이 필요하다. 이번 검토에서는 웹앱의 실제 배포 데이터까지 검증하지 않았다.
- `hyeoks_nightly.py:304`는 AA·AB를 읽고 단계별로 갱신하며, `hyeoks_morning.py:301`과 `385`도 소비한다. 장전만 사용하는 독립 캐시는 아니다.

## R3. 프로그램 필드 결측도 pgtr_ok=True가 된다

근거는 `omakase.py:2024`다.

실제 프로그램 조회 소스 블록을 가짜 HTTP 응답으로 실행했다.

| 응답 output | pgtr_ok | 결과 금액 |
|---|---|---|
| `{}` | True | 0.0 |
| `{"pgtr_ntby_qty":""}` | True | 0.0 |
| `{"pgtr_ntby_qty":"0"}` | True | 0.0 |
| `{"pgtr_ntby_qty":"100"}` | True | 0.01 (가상 가격 10,000) |

`out.get(...,"0")`와 `or "0"` 때문에 결측과 실제 0이 합쳐진다. API 성공 코드만으로 값 존재를 보장할 수 없다. 키 존재·빈 값·숫자 파싱을 확인한 경우만 성공 플래그를 설정하고 결측은 미확인으로 표시해야 한다.

장전 모듈은 별도의 0 표시 방어가 있어 이 오류가 장전에서 그대로 0으로 나온다고 단정하지 않는다. 하지만 스캐너 원자료와 이를 직접 받는 소비자에는 구분이 없다. analyst·scanner_bot이 프로그램 문자열을 받아 쓰는 경로도 있다. V2 점수·선정 조건을 이번 표시 수정에 섞어 바꾸지 않는다.
