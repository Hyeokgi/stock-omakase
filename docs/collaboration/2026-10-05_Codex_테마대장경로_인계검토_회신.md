# 테마·대장 후속 경로 연구 인계 검토 회신

작성일 2026-10-05. 검토자 Codex. 대상은 Claude 인계서 68f819b와 신규 연구 일봉·보고 구현이다.

## 1. 결론과 이번 작업 범위

연구 방향은 타당하다. 일별 대장 표시가 바뀌어도 최초 후보를 계속 추적하고, 종목 약화와 테마 소멸을 분리하며, 잠긴 연구 결과를 일일 보고에 넣지 않는 방향을 유지한다. 새로운 테마 공급자로 바꾸는 것보다 현재 수집의 시점·완전성·가격 기준을 먼저 바로잡아야 한다.

그러나 신규 연구 수집기를 현재 상태 그대로 완성됐다고 판단할 수는 없다. 첫 본격 수집 전에 아래 R1~R5를 보완하는 것을 권한다. 이는 기존 운영 선정이나 주문에서 새 장애가 발생했다는 뜻은 아니다.

이번에는 검토와 합성 재현만 했다. 운영 코드 수정·커밋·푸시, GitHub Actions 수동 실행, 텔레그램 발송, 시트 쓰기는 하지 않았다. 잠긴 확증 구간 수익률도 열람하지 않았다. 공동 허브 등록은 아직 하지 않았다.

근거 파일은 다음과 같다.

- [Claude 인계서](https://github.com/Hyeokgi/stock-omakase/blob/68f819b/docs/collaboration/2026-10-04_Claude_코덱스전달_테마대장경로_진행현황.md).
- [연구 수집·보고 모듈](https://github.com/Hyeokgi/stock-omakase/blob/68f819b/hyeoks_research_daily.py).
- [연구 예약 실행](https://github.com/Hyeokgi/stock-omakase/blob/68f819b/.github/workflows/research_daily.yml).

검토 모듈의 Git blob은 `88e84d256274ba64080ed163f56e10654d744748`이다. 검토 종료 전 최신 원격의 같은 파일도 이 값과 일치했다. 전체 원격 저장소가 이후에도 변하지 않는다는 뜻은 아니다.

## 2. 확인된 결함과 보완 순서

### R1. 부분 성공이 전체 초기 수집 완료로 취급된다. 중요도 P1.

근거는 `hyeoks_research_daily.py:172~188`, 특히 174행이다. 월별 파일이 하나라도 있으면 다음 실행은 모든 대상에 300봉 대신 5봉을 요청한다.

합성 재현에서 첫 실행의 A 종목은 성공하고 B 종목은 실패하도록 했다. 다음 실행에서 B도 5봉만 요청했다. 지수만 성공해 파일이 생기는 경우에도 같은 문제가 생긴다. 새 편입 종목의 과거 구간이나 5봉을 넘는 수집 공백도 자동 복구되지 않는다.

최소 보완은 종목별 수집 범위·초기 수집 완료 여부·미처리 목록을 보존하는 것이다. 전체 파일 존재 여부가 아니라 종목별 필요한 기간으로 요청량을 결정해야 한다. 상장 기간이 짧아 300봉이 없는 경우와 수집 실패도 구분한다.

### R2. 대상 거래일과 실제 실행일이 섞여 확정 봉을 버리거나 미확정 봉을 저장한다. 중요도 P1.

근거는 `hyeoks_research_daily.py:125~140`, 185행 및 257~261행이다. `run_bars()`가 대상 거래일을 `store()`의 `today`로 넘기지만, 미확정 판정은 실제 실행 시각의 시·분으로 한다.

두 경우를 재현했다.

| 실행 상황 | 현재 동작 | 필요한 동작 |
| --- | --- | --- |
| 10/7 01:00에 전날 10/6 수집 | 이미 끝난 10/6 봉을 미확정으로 제외 | 전날 확정 봉을 보존 |
| 10/6 14:00에 `--date 2026-10-02`로 재실행 | 10/2 봉을 제외하고 응답에 포함된 10/6 장중 봉을 저장 | 10/2 이후 자료를 해당 복구 실행에서 제외 |

대상 거래일, 실제 실행일, 봉 날짜, 수신 시각을 별도로 다뤄야 한다. 과거 날짜 복구는 대상일 이후 봉을 섞지 않고, 미확정 제외는 실제 현재 거래일에 적용한다. 새벽 8시를 넘는 예약 지연은 현재 날짜 추정 규칙으로 해결됐다고 볼 수 없다. 예약 회차 또는 명시적 대상일에 근거해야 한다.

덧붙여 현재 `fetchedAt`은 수백 종목 요청 전의 실행 시작 시각이다. 실제 수신 시각으로 바꾸거나 필드 이름을 시작 시각으로 명확히 해야 한다. 16시 이후 수신했다는 이유만으로 원천 가격 자체의 확정·수정주가 검증까지 끝난 것은 아니다.

### R3. 수집 결과가 실제 일일 보고로 전달되지 않는다. 중요도 P1.

근거는 `research_daily.yml:52~57,78~88`, `hyeoks_research_daily.py:285~299`다. 워크플로는 `--bars`와 `--report --send`를 서로 다른 프로세스로 실행한다. 보고 프로세스의 `bars`는 `None`이고, 수집 때 저장한 `last_run.txt`도 읽지 않는다.

합성 재현에서 요청 2·성공 1·실패 1을 파일에 남겨도 보고에는 그 숫자가 나오지 않았다. 전 종목 요청 실패나 텔레그램 발송 실패도 현재 CLI는 0으로 끝난다. 또한 커밋·푸시 실패 후 로컬에 있는 자료만 보고 원격 보관이 완료된 것처럼 읽힐 여지가 있다.

실행 ID와 대상일을 포함한 구조화된 상태 파일을 저장하고, 보고가 해당 실행의 상태를 읽게 해야 한다. 수집 성공, 대상일 자료 확보, 로컬 저장, 원격 반영, 발송 확인을 구분한다. 오래된 상태 파일을 오늘 성공으로 재사용하지 않는다. 연구 실패를 기존 생산 Gate에 전파할 필요는 없지만 연구 자체의 상태는 `DEGRADED` 또는 `FAILED`로 드러나야 한다.

### R4. 전체 요청이 끝나기 전까지 저장하지 않아 중단 시 앞선 성공분도 사라진다. 중요도 P1.

근거는 `hyeoks_research_daily.py:177~185`, `research_daily.yml:38`이다. 수집한 봉을 메모리에 쌓고 모든 요청 후 저장한다. 작업 제한 시간은 30분이다.

합성 재현에서 첫 종목은 성공하고 두 번째에서 실행 중단을 일으켰더니 저장된 성공분이 없었다. 초기 대상이 약 857개라면 요청당 10초 가까이 소비하는 구간이 길 때 30분 제한을 초과할 수 있다. 이는 실제 지연 시간을 측정한 주장이 아니라 코드의 중단 취약성이다.

대상을 제한된 묶음으로 처리하고, 종료 여유를 둔 시간 예산과 재개 위치를 보존하는 방식을 권한다. 임시 러너에 파일만 쓰고 종료되면 영속 보존이 아니므로 성공한 묶음·진행 상태가 원격에도 남도록 해야 한다. 제한 시간만 늘리는 것으로 R1의 누락 복구 문제는 해결되지 않는다.

### R5. 수치 정밀도와 가격 품질 검증이 부족하다. 중요도 P1.

근거는 `hyeoks_research_daily.py:48~74,138~139,179~188`이다.

- 저장 시 `:g`의 기본 6자리 유효숫자 때문에 거래량 `123456789`가 `123457000`으로 바뀌었다. 가격도 값의 자릿수에 따라 영향받을 수 있다.
- `20261340|nan|inf|-1|105|100`처럼 잘못된 날짜와 비정상 수치가 파서를 통과했다.
- 10/6 수집에서 10/1 봉만 돌려줘도 성공 1로 집계됐다. 응답 수신 성공과 필요한 거래일 자료 확보를 구분하지 않는다.

원천 숫자의 정밀도를 보존하고 실제 날짜·유한값·가격 관계를 검사해야 한다. 종목 식별, 최신 봉 날짜, 필요한 기간의 충족 여부도 따로 기록한다. 거래정지 등으로 0 또는 무거래 봉이 나오는 경우는 이유를 분리하며, 무조건 정상 가격이나 단순 파싱 실패로 뭉개지 않는다.

### R6. 잠긴 연구 상태표의 유효일 수가 본 분석기의 상한과 다를 수 있다. 중요도 P2.

근거는 `hyeoks_research_daily.py:214~219`다. `valid_hold_days()` 호출에 본 분석기가 사용하는 120거래일 상한을 넘기지 않는다. 합성 자료의 2027-12-30도 유효일 1개로 셌다.

이는 일일 상태표의 집계 불일치이며, 잠긴 본 분석기의 평가가 실제로 조기에 열렸다는 증거는 아니다. 검증된 달력으로 같은 상한을 적용하고, 달력 미확보 시 확정하지 못했다는 상태를 표시해야 한다.

현재 보고에서 수익률 숫자가 출력되는 경로는 발견하지 않았다. 내부에서 `with_returns=True`를 호출한다는 것만으로 결과 유출이라고 단정하지 않는다. 다만 `%` 문자가 없는지만 검사하는 시험은 충분하지 않다. 허용된 상태 필드만 출력하고 합성 수익률을 바꿔도 보고 본문이 변하지 않는지 검사하는 편이 강하다.

## 3. 요청받은 다섯 항목의 답

### ① 최근 20관측일 추적이면 충분한가.

초기 수집의 임시 범위로는 가능하지만, 연구 종료 기간이나 충분한 표본 기준으로 쓰면 안 된다. 현재 규칙은 오늘을 포함한 20관측일이므로 마지막 대장 등장 이후 20거래일 전체를 보장하지도 않는다. 관측 결손이 있으면 관측일과 거래일이 달라진다.

최초 대장 후보와 고정된 대조군을 에피소드 목록에 등록하고, 이후 배지 소실과 무관하게 추적한다. 수집 종료 시점을 따로 두되 미종결·결측·추적 종료를 구분한다. 20일 이후 경로를 연구할 가능성이 있다면 수집은 더 길게 이어가고 분석 기간은 나중에 결과를 보고 유리하게 고르지 않는다. 사용자의 질문은 고정 10일 수익률이 아니라 즉시 상승·횡보 후 상승·가격조정 후 회복·지속 약화의 예측이다.

### ② 처음 받은 값과 나중 수정값 중 무엇을 쓰는가.

원본 보관은 처음 값과 후속 수정 이력을 모두 남기는 현재 방향이 맞다. 그러나 분석에 서로 다른 조정 기준의 가격을 섞으면 안 된다. 과거 최초 값과 기업행사 후 가격을 단순 연결하면 가짜 급등락이 생길 수 있다.

관측 원본과 분석용 가격 계열을 분리한다. 당시 의사결정 입력은 그때 사용 가능했던 자료, 이후 성과는 기업행사와 조정 기준이 일관된 계열로 계산한다. 어느 쪽이 수익률이 좋다는 이유로 최초·최신 값을 선택하지 않는다. 조정 여부가 불명확한 종목 구간은 보류한다. 최근 5봉만 다시 받으면 더 오래된 수정주가 변경을 검출하지 못한다는 점도 남긴다.

### ③ `[연구]` 일일 보고에 넣고 뺄 항목.

넣을 것은 대상일·실행 시각·자료 기준시각, 요청 수·응답 성공·대상일 확보·실패·미처리 수, 초기 수집 진행률, 신규 행·수정 감지·품질 보류 수, 원격 보관 상태, 에피소드 수, 구조적 대장 교체 수, 결과를 공개하지 않는 잠긴 연구의 상태다.

잠금 해제 전에는 확증 구간 수익률, 승률, 후보별 이후 가격 경로, 조건별 성과 순위, 전일과의 차이로 이를 역산할 수 있는 누적 성과를 빼야 한다. 대장 교체는 현재 정의 아래의 표시 변경이며 실제 주도권 이전으로 단정하지 않는다. `[연구]` 보고는 기존 운영 알림과 구분하고 매수 추천으로 쓰지 않는다.

중복 발송과 응답 불명확 상태도 구분한다. 원격 저장 및 발송이 한 번이라도 검증되기 전까지 “가동 확인” 대신 “등록됨·첫 실행 미확인”으로 표시한다. GitHub 예약은 지연 또는 누락될 수 있어 19:40을 정시 보장으로 표현하지 않는다.

### ④ 자료 사전의 남은 세 관찰은 어떻게 해석하는가.

| 관찰 | 판단과 다음 확인 |
| --- | --- |
| 테마 순위 정확 일치 약 75% | 서로 다른 시점·동률 처리·정렬 정의를 먼저 맞춘다. 이 비율만으로 어느 한쪽 순위 오류라고 단정하지 않는다. |
| 구성 종목 수와 테마 통계 불일치 1,130테마-일 | 시장 전체 제공처 집계와 수집된 부분 모집단은 분모가 다를 수 있다. 동일 제공처·동일 시점의 상승/하락/보합 비율과 스캔 포착률을 따로 계산한다. |
| 뜨거운 테마의 연속 체류가 대부분 1일 | 순위 진출입에 민감한 정의의 결과다. 하루 순위 이탈을 테마 소멸로 부르지 않는다. 결측·휴장·실제 이탈을 구분하고 공백 허용 에피소드를 결과와 독립적으로 정한다. |

과거의 81% 대장 교체는 기존 일별 대장 정의의 변화율이다. 실제 경제적 주도권 교체율로 확대 해석하지 않는다. 네이버 분류는 관측 기준선으로 보존하고, 추후 뉴스 재료 또는 민간 분류는 출처·수집시각·당시 구성종목을 남기는 별도 비교 축으로 추가하는 편이 낫다. 민간 분류 도입이나 구매는 이번 검토에서 실행하지 않았다.

### ⑤ 원격에 없는 Codex 예비 코드는 어떻게 공유하는가.

로컬 `e25af04` 예비 코드와 `55da2f7` 문서 변경은 그대로 적용하는 것을 권하지 않는다. 예비 코드는 고정 10일·10% 질문을 다루며, 이후 명확해진 에피소드 경로 예측과 목적이 다르다. 별도 예약기를 함께 켜면 새 `research_daily.yml`과 중복될 수 있다.

재사용 가능한 부분은 원천 해시·실행 정보, 결측·미성숙·방화벽 상태 구분, 결과 추적이 확증 경계에 걸칠 때 차단하는 처리, 발송 중복·불명확 응답 처리다. 최신 구현 한 곳에 필요한 부분만 통합하고 연구 예약기도 하나만 유지한다.

이번 회신은 실제 Markdown 파일과 검토 ZIP으로 전달한다. Windows 경로 텍스트만 Claude에게 보내지 말고 파일을 첨부해야 한다. 원격 허브에는 Claude가 회신 원문을 등록한 뒤 링크를 남기면 된다. 문서를 전달한 것과 상대가 검토·승인한 것은 별개다.

## 4. 시험과 독립성

- 원격 신규 모듈의 기존 시험 13개를 재실행해 전부 통과했다.
- 추가 합성 검사 9개는 모두 기대한 안전 동작을 만족하지 못했다. 실패 9·실행 오류 0으로 위 결함을 재현했다. “22개 통과”가 아니다.
- 네트워크 연결을 차단하고 임시 폴더와 합성 값으로 실행했다. 새 확증 성과는 읽지 않았다.
- 저장소 전체 847개 시험을 이번 환경에서 재실행한 것은 아니다. Claude가 보고한 수치와 이번 확인을 구분한다.
- 실제 원천 응답, 최초 예약 실행, 원격 반영, 텔레그램 도착은 이번에 확인하지 않았다.
- Codex 예비 코드와 연구 종료·방화벽 개념에 대한 평가는 자기 검토 성격이 있다. 이번 신규 수집·보고 구현의 동작 검증은 Claude 구현에 대한 교차 검토다.
- 안정화 지문을 이번에 다시 계산하지 않았다. 검토용 파일만 만들었고 운영 파일은 바꾸지 않았다.

검토 ZIP의 `reproduce_review.py`는 발견 시점 동작을 재현하는 진단 도구다. 원래 시험 13개 통과 및 추가 9개 실패가 재현되면 종료코드 0을 내도록 작성되어 있으므로 일반적인 합격 CI로 넣으면 안 된다. 수정 후에는 각 안전 동작 시험이 통과하는 정상 회귀시험으로 옮겨야 한다.

재현하려면 저장소 의존성이 준비된 환경에서 ZIP을 별도 폴더에 풀고 `RESEARCH_REPO` 환경변수에 저장소 경로를 지정한 뒤 진단 도구를 실행한다. ZIP 안에는 검토한 원격 모듈·기존 시험·워크플로 사본을 포함한다. 스냅샷은 포함하지 않는다. 기존 시험이 참조하는 공개 스냅샷과 저장소 모듈이 필요하다.

## 5. 권고 작업 순서와 완료 조건

1. 먼저 R2 날짜 처리와 R5 원천 숫자·품질 검증을 고친다. 합성 자정·과거 복구·비정상 값·원천 숫자 왕복 시험이 통과해야 한다.
2. R1 종목별 미처리 복구와 R4 제한된 묶음 수집을 연결한다. 일부 실패나 중단 뒤 다시 실행해 필요한 구간이 빠짐없이 복구되는지 확인한다.
3. R3 수집·보관·보고 상태를 연결한다. 실패 주입 시 `[연구]` 보고가 해당 실패를 실제 건수와 원인으로 표시하고 기존 생산 Gate와는 분리되는지 확인한다.
4. R6 상태표도 본 연구의 달력·상한을 공유하게 한다. 잠긴 수익 결과는 계속 비공개로 둔다.
5. 첫 생산 회차에서 원격 저장 내용을 다시 읽고 대상일·건수·수치·미처리 목록을 대조한다. 텔레그램 도착도 별도 확인한다. 그때 “첫 수집·보고 검증 완료”로 기록한다.

공개 원천에서 읽을 수 있다는 사실과 대량 원자료의 재배포 허용은 별개다. GitHub 공개 보관에 대한 사용자 의사와 제공처의 저장·재배포 조건을 구분해 확인할 필요가 있다. 이번에는 이용조건 준수 여부를 확정하지 않았다.

관련 운영 참고는 [GitHub 공식 예약 실행 문제 해결 안내](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows)다. 예약 등록 자체를 실제 실행 성공의 증거로 취급하지 않는다.
