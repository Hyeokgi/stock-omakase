**R1. 게이트 구현은 진행하되, 생산 정책 변경 없이 완성한다.**

근거는 [전략로드맵 §3-5-7의 확정 커밋 `b4ededd`](https://github.com/Hyeokgi/stock-omakase/commit/b4ededd)과 현재 `hyeoks_verdict.py:545`, `:1090`이다. 현재 정책 필터는 리포트 신호일에 의존하며, 명목 Holm 계산 뒤 `passed`를 비운다. 따라서 게이트 함수 추가만으로는 정책 결속이 해결되지 않는다.

수정 범위는 `hyeoks_verdict.py`, `.github/workflows/verdict.yml`, 관련 `tests/`, 작업 문서다. `rank_pool.py`, `omakase.py`, `hyeoks_tajeom.py`, `hyeoks_analyst.py`, 동결·안정화 생산 코드는 이번 구현 범위에서 유지한다. 이 범위는 `stability_gate.py:42`의 지문 목록에 포함되지 않으므로 **10/12부터 시작하는 `3858ca931dde` 연속 판정과 충돌하지 않는다.**

구현 순서는 다음과 같이 확정한다.

1. **정책 결속을 먼저 구현한다.** 원장 행과 실행 ID·영수증·동결 묶음·실행 코드·실제 설정을 연결한다. 기존 `policy_id`는 원문대로 보존하고, 증거로 확인한 채널별 정책과 cohort를 판정 단계에서 별도로 식별한다. 날짜나 정책 ID 문자열만으로 인증하지 않는다. 연결 누락·모순·모호성이 있으면 해당 판정을 닫는다.
2. **C/E/L 게이트를 분리한다.** C는 고정 결정일·α 0.0125·Holm `m=2`, E는 고정 블록별 `N≥30`·단측 `p<0.05` 및 연속 두 블록 재통과를 적용한다. L은 전용 사전등록이 확정되기 전까지 `LONG_RULE_NOT_PREREGISTERED`로 닫는다.
3. **부트스트랩과 `decision_*`를 연결한다.** 날짜별 짝 차이, 블록 길이 H, 10,000회, 시드 20260913을 유지한다. 승인용 성숙도는 검증된 거래일 달력으로 확인한다. 현재 `maturity_note()`의 달력일 근사와 `None`을 승인 근거로 사용하지 않는다.
4. **시험·교차 검토 후 마지막으로 `passed`를 연결한다.** 실제 자료가 요건을 만족하지 못해 계속 비어 있는 것도 정상 결과다.

평가일 차단은 **수익률 집계·출력보다 앞에** 둔다. 현재 `hyeoks_verdict.py:2026`은 보고서 생성 전에 집계하며, 판정 워크플로는 별도 스위치 검사도 실행한다. 따라서 블록 A 평가 요청이 아직 열람할 수 없는 B·C·L 결과나 다른 분석을 함께 출력하지 않도록 실행 범위를 제한한다.

검증은 합성 자료로 수행한다. 정책 연결 실패, cohort 혼합, 평가일 전 실행, 달력 범위 밖, 미성숙, E의 1차만 통과한 경우, 대조군의 승인 제외를 시험한다. 전체 회귀시험과 Codex 검토가 끝나기 전에는 상수 보류를 해제하지 않는다.

**R4. 블록 A는 정책 불변과 증거 연결을 따로 확인한다.**

지금 확인한 사실은 `hyeoks_tajeom.py:25`의 정책 상수가 유지되고, 리포트 관련 주요 코드에서 블록 A 시작 이후 변경이 확인되지 않았다는 것이다. **실제 운영 표본의 정책 연결은 이번에 검증하지 않았다.**

`docs/정책변경_체크리스트.md` §0~2는 환경변수만 바뀌어도 정책 상수는 그대로일 수 있다고 명시한다. 따라서 PC Claude는 다음을 결과 열람 없이 확인한다.

블록 안에서 리포트 선정 정책이 실제로 변경되면 해당 채널의 A 블록을 무효로 처리한다. ID 갱신 누락으로 무효화를 피하지 않는다. 증거가 부족한 경우는 **정책 변경 확정과 구분해 검증 불가로 보류**한다. 표본 부족 역시 블록 무효와 다른 상태다.

**위험은 정책 상수·지문·추천 코드 중 하나만 같으면 블록이 유효하다고 오판하는 것이다.** 반대로 지문 변경만으로 모든 채널의 연구 블록을 일괄 무효화하지도 않는다.

**R5. 10/9 첫 적재 제한은 두 트랙 C 채널의 cohort 경계다.**

근거는 [변경 커밋 `c623b5c`](https://github.com/Hyeokgi/stock-omakase/commit/c623b5c), `omakase.py:3459`, 전략로드맵 §3-5-7 U3다.

변경 전에는 채널 상한에 미달한 경우 뒤 실행에서 새 후보가 추가될 수 있었다. 변경 후에는 **스캐너 채널 중 어느 하나라도 그날 적재됐으면**, 차트·수급 채널이 비어 있거나 상한 미달이어도 추가하지 않는다. 점수 공식이 같아도 **표본에 들어갈 수 있는 시점과 후보 집합이 달라진다.** 따라서 선정 정의 변경으로 판단한다.

정책 변경 커밋일은 10/9로 기록하고, 표본 경계는 변경 코드가 실제 적용된 첫 실행으로 확정한다. 예정대로라면 10/12부터다. PC Claude가 첫 운영 영수증과 실행 SHA로 확인하며, 날짜만으로 소급 인증하지 않는다.

`rank_pool.py:56`의 기존 ID에는 첫 적재 규칙이 표현되지 않는다. R1에서는 기존 ID와 실행 코드·설정 증거를 함께 사용해 전후 cohort를 구분한다. 원자료 ID를 덮어쓰거나, 기존 ID가 같다는 이유로 합치지 않는다. 이력으로 분류할 수 없으면 `channel_policy_unverified`로 닫는다.

프로그램 조회 실패 표시·장전 시간외 보존·같은 실행 내 append 재조회는 확인한 범위에서 별도의 선정 경계를 만들지 않는다. 단, 첫 적재 제한과 묶여 배포된 사실은 기록한다.
