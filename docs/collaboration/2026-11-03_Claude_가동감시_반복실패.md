## 2. 원인 — 감시 스크립트가 manifest 형식 변화를 못 따라갔다

`2220_1288679_1` · `2220_1288680_1` 은 9/15 첫 실행 오탐 때 확인한 같은 PDF 재게시 쌍이다. Drive 에는 원본(`…679_1`) 파일 하나만 있다(Drive 조회로 확인).

- 10/11 manifest: `…680_1` 기록의 `duplicate_of` = `2220_1288679_1` → 감시가 중복으로 빼서 정상.
- 10/17 manifest 부터(11/01 까지): 같은 기록의 `duplicate_of` 가 **null**. 대신 `drive_file_name` 과 `drive_id` 가 원본 파일을 가리키고, sha256 도 원본과 같다. 즉 **연결은 남아 있고 표시 필드만 바뀌었다.** 10/17 실행은 첨부 66개를 다시 받았고(`revised_pdfs` 1) 이때 기록이 다시 쓰인 것으로 보인다(추정).
- 감시는 `duplicate_of` 만 보므로 `…680_1` 을 '파일 없음' 으로 셌다.

수집 장애도, 깃허브 예약 지연도 아니다. 실행 시각은 월 13:34~14:56 KST(예약 09:10 보다 4.5~6h 늦음)지만 판정 기준은 '직전 예정 수집(일 21:00)' 이라 늦게 와도 결과가 같다.

## 3. 10/19 의 수집지연 6건은 실제였다

Drive 최신 보관 시각이 10/17 21:05 였고 10/18(일) manifest 가 없다 — **일요일 수집이 돌지 않았다.** 10/24 실행에서 메워져 10/26 부터 미수집 0. 이번 수정과 무관하며, 그 주에는 고쳐도 `exit 2` 로 실패했을 것이다(의도된 동작).

## 4. 수정

`manifest_ids()` 에서 `duplicate_of` 가 있거나 **`drive_file_name` 의 source_id 가 자기 것이 아니면** 중복으로 본다.
원본 기록은 자기 파일명을 가리키므로, 원본 파일이 지워지면 여전히 gap 으로 잡힌다(9/15 false negative 방어 유지).
