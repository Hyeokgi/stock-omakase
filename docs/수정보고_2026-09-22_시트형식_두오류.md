# 9/22 Gate 를 막은 두 오류 수정 — 시트 표시 형식과 잔여 행

승인: 사용자 + 코덱스 합의(2026-09-22 21:30 KST 시트 직접 확인).
범위: **이 두 오류만.** 선정 문턱·점수 공식·Gate 기준·계측 등급은 건드리지 않았다.

두 오류는 성격이 같다. **데이터가 없는 것이 아니라, 정상적인 시트 상태를 코드가
읽지 못한 것**이다. 그래서 "빈 종목에 몇 점을 줄 것인가" 같은 전략 판단이 아니다.

## ① `1,938억원` 을 읽지 못했다 — theme_money 4,132건

`get_all_values()` 는 저장된 숫자가 아니라 **표시 형식이 적용된 문자열**을 돌려준다.
`거래대금(억원)` 칸은 `omakase.py:666` 에서 `int()` 로 쓰이지만 읽을 때는
`1,938억원` 으로 온다. 쉼표만 지우고 `int()` 하면 **전부** 실패한다.

이 저장소는 같은 실수를 이미 두 번 따로 겪었다.

| 위치 | 대상 | 그때 처리 |
|---|---|---|
| `hyeoks_analyst.py:759` | 수급_실시간 | `re.sub(r'[^0-9]','')` 로 때움 |
| `hyeoks_analyst.py:788` | 수급_Raw | 쉼표만 지움 → **전부 실패** |

`[^0-9]` 전부 제거는 단위를 해석한 것이 아니다. `1.2조원` 을 `12` 로 만들고
음수 부호도 지운다. 그래서 `krx_code.py` 와 같은 방식으로 규칙을 한 곳에 두었다.

**신규 `krx_amount.py` (`krx-amount-v1`, 자체 검증 20건)** — 셋을 구분한다.

- `ok` 숫자로 읽었다
- `missing` 칸이 비었다. **오류가 아니라 결측이고 0 이 아니다**
- `bad` 값이 있는데 못 읽는다. **여전히 CRITICAL 로 운다**

허용 단위는 열이 선언한 `억원`·`억` 뿐이다. `원`·`조원` 은 받지 않는다 —
받아 주면 1억 배 틀린 값을 조용히 더하게 된다.

`수급_Raw` 경로만 이 규칙으로 바꿨다. **`:759` 의 수급_실시간은 이번에 건드리지
않았다** — "두 오류만" 범위를 지켰다. 정상 데이터에서 두 방식의 답은 같다.
다만 같은 열에 규칙이 둘 남아 있으므로 3거래일 판정 뒤 통일을 제안한다.

## ② 정리 범위가 출력 폭보다 한 열 짧았다 — 잔여 행 2개

`omakase.py` 는 `extended_headers` **34열(A~AH)** 을 쓰는데 남은 행을 지우는 범위가
`A{n+1}:AG` **(33열)** 로 굳어 있었다. 종목 수가 줄어든 날 **AH(RS등급)만 남은 행**이
생긴다. 9/22 `주가데이터_보조` 729·730행에 39·77 이 그렇게 남아 있었다.

analyst 는 그 행을 종목으로 읽었다. 종목코드가 비어 `zfill(6)` 이 `000000` 을 만들고,
V1/V2 칸도 비어 `int("")` 가 터졌다 — 9/22 영수증의 `v1·v2 각 2건`이 이것이다.

- `omakase.py`: 끝 열을 **실제 출력 폭에서 계산**한다(`_col_letter(len(extended_headers))`).
  헤더가 늘어나도 다시 어긋나지 않는다. 고정 문자열 `AG` 를 지웠다.
- `hyeoks_analyst.py`: 후보 루프가 `krx_code.normalize()` 로 **종목 여부를 먼저 판정**한다.
  저장소의 공유 규칙이고 `000000` 은 `NOT_A_CODE` 로 이미 거부된다.
- **제외 건수와 사유를 남긴다** — 로그 한 줄과 영수증 `payload.excluded`
  (`invalid_rows`, `reasons`, `theme_money_missing`). 조용히 버리지 않는다.

시트에서 두 행만 손으로 지우면 재발 원인이 남으므로, 원인인 정리 범위를 고쳤다.

## 🔴 반드시 알고 넘어갈 부작용 — 잠자던 필터가 깨어난다

`raw_theme_daily_map` 은 집계용이 아니라 **후보 검증에 들어간다.**

```python
theme_val_eok = raw_theme_daily_map.get((f_date, clean_theme), 0)
if theme_val_eok >= 2000 or theme_val_eok == 0:     # hyeoks_analyst.py:260
    has_qualified_day = True
```

파싱이 전부 실패하던 동안 이 맵은 **사실상 비어 있었다.** 모든 조회가 `0` 을 돌려주고
`== 0` 가지가 늘 참이었으므로, **테마 대금 조건은 작동하지 않았다.** 후보는
하루 700억 거래대금만 넘으면 통과했다.

맵이 채워지면 이 필터가 실제로 거르기 시작한다. 문턱(2000억)을 바꾼 것이 아니라
**원래 쓰여 있던 필터가 제 일을 하게 되는 것**이다. 그래도 내일 15시 회차부터
`DNA검증` 단계 통과 수가 달라질 수 있다.

영향은 기존 계측으로 그대로 보인다 — 로그의
`(상위관문: 원시 N → 점수선별 N → DNA검증 N → 풀 N)` 과 영수증의 `upstream`.
탈락률 80% 이상이면 인프라 장애로 보고 점수순 폴백하는 가드(`:947`)도 그대로다.

### 날짜 칸 확인됨 — 조회는 맞는다 (2026-09-22 사용자 확인)

`수급_Raw` 날짜 칸은 `2026-09-22` 그대로 표시된다. `get_all_values()` 가 돌려주는
문자열이 곧 이것이므로 `(날짜, 테마명)` 조회는 어긋나지 않는다. 중복 폭증도 없다 —
`omakase.py:750` 의 `row[0] != today_str` 비교가 제대로 걷어내고 있다는 뜻이다.
**따라서 필터는 실제로 깨어난다.**

### 🔻 정정 — 효과는 작을 가능성이 높다

위에서 "DNA검증 통과 수가 크게 달라질 수 있다" 고 쓴 것은 **과했다.** 바로잡는다.

`omakase.py:664` 가 하루에 **테마를 최대 10개**만 기록한다(9/22 는 14행). 즉 맵의
키는 하루 10개뿐이다. 반면 `validate_stock_historical_dna` 는 후보의 **250일치**
가격 이력을 훑으며 매 고거래대금 일자마다 `(그날, 후보의 현재 테마명)` 을 찾는다.

- 후보의 현재 테마가 **그날 상위 10개 안에 있었을 때만** 키가 맞는다.
- 나머지 날은 전부 조회 실패 → `0` → `== 0` 가지 → **통과**.
- 게다가 `has_qualified_day` 는 250일 중 **하루만** 만족하면 된다.

그래서 후보가 탈락하려면 "700억 넘긴 모든 날이 하필 자기 테마가 상위 10위였고
그 기록 대금이 2000억 미만이었던 날" 이어야 한다. 매우 좁은 조건이다.
**대부분의 후보는 그대로 통과할 것으로 본다.**

바뀐 것은 분명하다 — 그동안 이 필터는 **한 번도 작동한 적이 없었고** 이제 작동한다.
다만 그 효과의 크기를 크게 잡을 근거는 없다. 내일 `DNA검증` 단계 수로 확인한다.
큰 폭으로 움직이면 그때 원인을 따로 본다.

`원시` 수는 727 → 725 로 줄어 보일 텐데 이는 **자료 손실이 아니라** 종목이 아닌
2행을 더 이상 종목으로 세지 않는 것이다.
