## 1. 🔴 P0-1 — V3 열 계약 오류 (확인, 수정)

지적대로다. 확인한 사실:

```
EARNINGS_HEADER[8]  = 영업이익증감률(QoQ,%)
EARNINGS_HEADER[10] = V3(실적점수)          ← 진짜 V3

omakase.py:2686       int(row[8])   → 🔻실적 악화 주의 배지
hyeoks_analyst.py:782 int(row[8])   → v3_score
hyeoks_analyst.py:814 if is_structural_seed and v3_score is not None and v3_score < 20: continue
```

표시가 아니라 **후보에서 빠진다.** 그리고 프롬프트에 `실적점수(V3):N점` 으로 들어가며
`hyeoks_analyst.py:991` 이 AI 에게 "실적점수가 낮게 명시된 종목은 기술적으로 좋아 보여도
피하십시오" 라고 지시한다. 틀린 값이 두 경로로 선정에 들어갔다.

### 왜 조용했는가 — 두 상태가 섞인다

`try: int(row[8]) except Exception: pass` 였다. QoQ 는 `round(pct, 1)` 이므로

- **소수**(`"12.3"`) → `int()` 실패 → V3 가 **없는 것처럼** 처리 → 필터가 꺼진다(fail-open)
- **정수**(`"-8"`) → 통과 → 그 값이 **V3 로 쓰인다** → `-8 < 20` 이라 구조적 SEED 를 제외

즉 대부분의 날 V3 필터는 사실상 **작동하지 않았고**, 일부 종목은 **틀린 근거로 탈락**했다.

### 화석 — 원인은 특정했다(시점은 못 했다)

수집기가 시트를 새로 만들 때 아직 `cols="12"` 를 쓰고 있었다. **12열 시대에는 V3 가
index 8 이 맞았다.** 이후 `summarize()` 주석에 적힌 YoY 이관으로 `매출증감률(YoY,%)`·
`영업이익증감률(YoY,%)` 두 열이 5·6 에 끼어들면서 V3 가 10 으로 밀렸고, 소비자는 8 에 남았다.
저장소 이력이 그 이관보다 뒤에서 시작하므로 **날짜는 git 으로 알 수 없다.**

### 조치 — 숫자를 다시 박지 않았다

새 모듈 `earnings_schema.py` 를 생산자·소비자가 공유한다.

- 위치를 **이름으로** 찾는다(`locate(sheet_header, "V3(실적점수)")`). 열이 또 움직여도 따라간다
- 헤더가 **없거나 중복이거나** 다르면 → V3 를 쓰지 않고 `❌ [V3 사용 중단] <사유>` 를 찍는다
- 값 **범위 0~100** 을 검사한다. 범위 밖이면 쓰지 않고 세며
  `"범위밖이 있으면 다른 열을 읽고 있다는 신호다"` 를 로그에 남긴다.
  **이 검사 하나만 있었어도 QoQ 오독은 첫날 잡혔다.**
- `except: pass` 를 없앴다. 빈칸/해석불가/범위밖을 각각 세어 매 실행 한 줄로 보고한다

## 2. 영향 범위를 여기서 셀 수 없는 이유 (질문 2)

세 가지가 겹친다.

1. **자격증명이 없다.** 이 작업 환경에 `secret.json` 이 없어 DB_실적 을 읽을 수 없다.
   시트에 지금 몇 행이 정수 QoQ 를 갖고 있는지 측정이 불가능하다.
2. **필터의 증거는 "빠진 것" 이다.** `continue` 로 탈락한 후보는 어디에도 기록되지 않는다.
   백테스트_로그에는 **선정된 것만** 남는다.
3. **시작 시점을 모른다**(질문 1).

그래서 숫자를 지어내지 않는다. 대신 **읽기 전용 프로브**를 제안한다 —
`hyeoks_sheet_probe.py` 와 같은 방식으로 DB_실적 을 읽어

```
전체 행 / V3 열 사용 가능 수 / row[8] 이 정수라서 옛 경로에서 쓰였을 행 수
/ 그중 row[8] < 20 이라 제외됐을 행 수
```

를 찍는다. 이걸 돌린 뒤에야 `affected / unaffected / unknown` 을 말할 수 있다.
**승인해 주시면 다음 커밋에서 만든다.** 과거 행은 고치지 않고, 필요하면
`V3_INPUT_SCHEMA_BUG` 라벨만 붙인다.

## 3. 🔴 P0-2 / P0-3 — 내 앞 커밋의 fail-open 둘 (확인, 수정)

둘 다 **어제 내가 만든 것**이다. 지적이 정확하다.

**P0-2** `except: existing_earnings = []` 후에도 본표에 썼다. 못 읽었다고 시트가
빈 것은 아니다. 빈 목록으로 병합하면 새 데이터가 위쪽만 덮고 **아래쪽 옛 행이 고아로
남는다.** `batch_clear` 가드도 `0 > N` 이라 돌지 않는다. 내 `clear()` 제거가
오히려 이 구멍을 열었다.
→ `earnings_readable` 플래그. 못 읽으면 **본표를 건드리지 않는다.**

**P0-3** 스키마 불일치에 `out_sheet.clear()` 후 새로 썼다. "해석할 수 없으니 전부
지운다" 는 fail-closed 가 아니다. 예산에 걸린 부분 실행이면 127종목으로 전체를 대체한다.
→ `clear()` 제거. 본표 무수정 + 실행 실패.

**둘 다 오늘 수집분은 버리지 않는다** — `stage_earnings()` 가
`data/earnings_staging/<타임스탬프>_earnings.csv` 로 쓰고, 워크플로가
`actions/upload-artifact` 로 꺼낸다(30일 보관). 컨테이너는 사라지므로 파일만으로는 부족하다.
"멈추는 오류가 틀린 값보다 낫다" 가 "모은 것을 버린다" 는 뜻은 아니라고 읽었다.

## 5. 🔴 §5 — DART/컨센서스 실행 분리 (수정)

지적이 맞다. 그리고 이게 **시간 예산 초과의 진짜 원인**이었다.

```
이전: for 종목: DART → 컨센서스(최대 12초 타임아웃) → sleep → 다음 종목
```

127건 실패면 타임아웃만 ≈25분이고, 그게 55분 예산을 먹어 DB_실적 이 127/143 에서 잘렸다.
즉 **"DART 가 느리다" 가 아니라 "보조가 주의 예산을 먹는다"** 였다. 내 앞 보고서는
이 둘을 별개 항목으로 적었는데, 하나의 원인이었다.

```
지금: PHASE A  143종목 DART → DB_실적 저장·확정
      PHASE B  preflight → 컨센서스 배치 → DB_컨센서스
```

**preflight**(§13 반영): 대조 종목 2개(005930·000660)로 원천 상태를 먼저 본다.
둘 다 실패하면 **그날 배치를 시작하지 않는다.** 143종목을 다시 때려 보고 원인을
추측하는 대신 두 줄로 상태를 얻고, DART 예산을 지킨다.

## 6. 🔴 §6 — 컨센서스 부분 성공 (수정)

지적이 내 보고보다 정확했다. 이전 코드는

```python
if consensus_failures:      # 1건만 실패해도
    raise SystemExit(1)     # ← 여기서 끝
if len(consensus_rows_out) > 1:
    ... 시트에 쓴다          # ← 도달하지 않는다
```

**1건 실패가 142건 성공 갱신을 통째로 버렸다.** 지금은 성공분을 먼저 쓰고 그 다음에
상태를 판단한다. 상태는 `OK / DEGRADED / FAILED / SKIPPED` 이고
`시도·성공·실패` 를 매 실행 한 줄로 남긴다.

종료코드(§7·Q1 반영): **주 산출물(DB_실적) 실패 → 적색. 보조는 완전 붕괴(FAILED)만 적색.**
DEGRADED 는 경고 + 초록.
**커버리지 문턱 숫자는 넣지 않았다** — 원인 조사 후 사전 고정하라는 지적대로다.
시험이 그 자리에 90% 같은 숫자가 없는지 확인한다.

## 7. §7 / §10 / §12 — 받되 범위를 나눈 것

**§7 워크플로 분리** 동의한다. 다만 이번에는 스크립트 안 PHASE 분리까지만 했다.
장애 격리 효과의 대부분(예산·주 데이터 확정)은 이미 나오고, 워크플로 분리는
`concurrency` 락·시트 인증·스케줄을 새로 잡아야 해서 별도 변경으로 올린다.

**§10 CI 트리거** 수정했다. 다만 제안하신 `.github/workflows/**/*.yml` 대신
`.github/workflows/*.yml` 을 썼다. `**/` 가 **디렉터리 0개를 매치한다는 보장이 없어**
최상위 `main.yml` 을 놓칠 수 있기 때문이다 — 이번에 고친 것과 같은 계열의 조용한 사고가 된다.
워크플로는 하위 디렉터리에 놓일 수 없으므로 단일 레벨이 맞다.
시험이 `**/` 패턴을 **금지**한다.

**§12 except 재분류** 지적을 받는다. "시트 쓰기가 0곳이므로 낮은 우선순위"는
틀린 판단이었고, 이번 V3 오류가 바로 반례다. 개수가 아니라 영향으로 다시 셌다(§8).
