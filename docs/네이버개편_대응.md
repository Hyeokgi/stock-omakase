### ⚠️ 캐치올 함정 (반드시 기억할 것)

`stock.naver.com/api/domestic/market/{이름}/list` 는 **존재하지 않는 이름에도 HTTP 200 + `[]`** 를 준다.

```
theme                  → 200, 20개
group                  → 200, 20개
upjong                 → 200, 79개    ← 업종의 올바른 이름은 이것이다 (pageSize=200)
industry               → 200, []      ← 영어 이름은 안 먹는다. upjong 을 쓸 것
completelyBogusName123 → 200, []      ← 아무 이름이나 []
```

즉 이 API로 이관할 때 **200을 성공으로 간주하면 안 된다.** 반드시 건수와 필수 필드를 검증해야 한다.

`hyeoks_market_snapshot.fetch_sector_data()` 가 이 가드를 구현한다 — 최소 건수(업종 40·그룹사 30)와
필수 필드(`no`·`name`)를 확인하고, 미달이면 그 축 없이 진행한다. 헬스체크 `upjong_json`·`group_json`
도 목록 건수만이 아니라 **가장 큰 분류의 구성종목까지** 받아본다(껍데기 200을 거르기 위함).

#### ⚠️ 또 하나의 조용한 실패 — pageSize 누락과 초과

이 계열은 `pageSize` 를 어떻게 주느냐에 따라 **셋 다 다르게 실패한다.** 실측(2026-08-28):

| pageSize | 결과 |
|---|---|
| 없음 | **200 + 20건** — 조용히 잘린다. 가장 위험하다(에러가 안 난다) |
| 100 ~ 200 | 정상 |
| 250 이상 | **HTTP 400** — 통째로 실패한다 |

그래서 최소 건수 가드를 **기본 응답 20건보다 높게** 잡아야 pageSize 누락을 잡을 수 있다.

### ① 🚨 위험종목 게이트가 통째로 열려 있었다

`hyeoks_static_collector.py`가 `value_input_option="USER_ENTERED"`로 문자열 `"True"`를 쓰면
구글시트가 이를 **불리언으로 해석**해 `TRUE`로 저장한다. 그런데 `omakase.py`는

```python
'is_junk': row[3] == 'True'      # 'TRUE' == 'True' → False
```

로 비교하고 있었다. 결과적으로 **DB_정적데이터의 275종목 전부가 `is_junk=False`** 로 읽혔다.

실제 피해 — 백테스트_로그 282건 중 **13건이 위험종목 명단과 겹쳤다.**

```
2026-08-11  리포트TOP2_단기  혜인          2026-07-31  리포트TOP2_단기  성호전자
2026-08-11  수급TOP2       NHN           2026-08-11  수급TOP2        코스메카코리아
2026-07-20  차트TOP2       누보           2026-07-10  차트/수급TOP2    대한광통신  …
```

**수정** — 대소문자·공백 무관하게 판정하는 `_sheet_bool()` 도입. 실데이터 검증에서
`수정 전 0종목 → 수정 후 275종목`으로 게이트가 복구되었다.

## 5-2. 실제로 구현한 이중화 (2026-08-26)

**설계 원칙: HTML이 '주', JSON이 '보조'.** HTML이 살아있는 동안 결과가 완전히 동일하므로
9/7 기준선이 흔들리지 않고, `finance.naver.com`이 죽으면 자동으로 JSON이 받는다.

| 지점 | 동작 |
|---|---|
| `hyeoks_static_collector.py` 위험종목 | **합집합** — HTML ∪ JSON. 실측 HTML 274 ∪ JSON 270 = 274 |
| `omakase.py` 테마 순위 | HTML 테이블 없으면 → `fetch_theme_list_json()` |
| `omakase.py` 테마 구성종목 | `type_5` 없으면 → `fetch_theme_stocks_json()` (단위 백만원으로 정규화) |
| `omakase.py` 주요뉴스 | 파싱 0건이면 → `fetch_main_news_json()` |
| `omakase.py` 검색상위 | 파싱 0건이면 → `fetch_search_ranking_json()` |
| `omakase.py` 뉴스 키워드 | 제목 0건이면 → `fetch_flash_news_titles(180)` (표본 크기 정렬) |
| `omakase.py` 주요일정 | 제목 0건이면 → `fetch_flash_news_titles(15)` |
| `omakase.py` 시가총액 | HTML 파싱 실패면 → `fetch_market_cap_json()` |
| `hyeoks_analyst.py` 종목뉴스 | 파싱 0건이면 → `fetch_stock_news_json()` |

**fail-closed 판정도 이중화했다.** 수집기는 이제 "HTML 관리종목 건수" 단독이 아니라
**"두 소스 중 하나라도 정상인가"** 로 판정한다. 한쪽만 죽으면 진행하되 텔레그램으로 알리고,
둘 다 죽어야 중단(전일 스냅샷 보존)한다.

또한 시트 기록을 `USER_ENTERED` → **`RAW`** 로 바꿨다. §4①의 `'True'`→`TRUE` 변질을
근본에서 막는다(omakase 쪽 `_sheet_bool()`은 이중 안전망으로 유지).

## 5-3. 수급(frgn) 폴백 — 앞선 우려는 실측으로 해소되었다 (2026-08-26)

처음에는 "HTML 5일치 vs JSON 10일치라 V2 점수가 바뀐다"고 판단해 폴백을 보류했다.
**이 판단은 틀렸다.** JSON의 앞 5개만 잘라 쓰면 값이 완전히 같다.

5종목 × 5일 전수 대조 — 날짜·종가·기관순매수·외국인순매수 **네 값이 자릿수까지 100% 일치**.

```
005930  2026.08.25  HTML 외국인 -5,003,317 / 기관 +203,484
        20260825    JSON 외국인 -5,003,317 / 기관 +203,484   ← 동일
```

누적 로직을 '수집'과 '계산' 두 단계로 분리하고, 계산부는 한 벌만 남겨 소스가 바뀌어도
갈라지지 않게 했다. 회귀 검증 결과 **구 경로 / 신 경로(HTML) / 신 경로(JSON 강제)**
3자가 기관누적·외인누적·쌍끌이일수·당일수급까지 6종목 전부 일치했다 → **V2 점수 무변화.**

### 종목별 수급 소스는 2단 폴백 (둘 다 HTML과 동일 검증)

| 순위 | 엔드포인트 | 비고 |
|---|---|---|
| ① | `stock.naver.com/api/domestic/detail/{code}/trend?tradeType=KRX&pageSize=20` | 신규 PC 사이트가 실제로 쓰는 경로. `pageSize` 200까지 가능 |
| ② | `m.stock.naver.com/api/stock/{code}/trend` | 구 모바일 API(10일 고정). 이 계열은 `/api/search/all` 사망 전례가 있어 2순위 |

**①을 1순위로 둔 이유** — `m.stock.naver.com/api/*` 는 구 모바일 API이고, 실제로 그 계열의
`/api/search/all` 이 이번 개편으로 이미 죽었다. 반면 ①은 새 사이트가 현재 쓰는 경로다.

#### ⚠️ `tradeType` 은 반드시 `KRX`

`NXT`(대체거래소) 체결분만 담기므로 값이 완전히 다르다. 008930 기준 —

| 날짜 | KRX 외국인 | NXT 외국인 |
|---|---|---|
| 2026-08-25 | **−22,404** | **+1,290** |
| 2026-08-24 | **−400,489** | **−2,231** |

부호까지 뒤집힌다. NXT로 받으면 수급 판정이 정반대가 된다.

### ⚠️ `trendForeignOrg` 는 이 용도로 쓸 수 없다

`/api/domestic/market/trend/trendForeignOrg` 는 **시장 전체 순위표**다(투자자별 매매동향 화면).

| 확인 항목 | 결과 |
|---|---|
| 응답 구조 | `sections.buyRankList` / `sellRankList` 각 최대 100건 |
| **종목 지정** | **불가.** `itemCode`/`itemcode`/`code` 파라미터가 전부 **무시**된다 |
| `pageSize` | 100에서 상한 (전종목 2,877 커버 불가) |
| `tradeType=KRX` | 장중엔 `estimated: true`, `accTradeAmount: 0` — 잠정 추정치 |
| `tradeType=NXT` | NXT 거래분만. 삼성전기 순매수 28,055 vs 당일거래량 574,386 — **전체의 일부** |

우리가 필요한 건 "스캔 대상 100~200종목 각각의 5일치"인데 이 API는 "상위 100위 랭킹"만 준다.
구조적으로 대체 불가다. **종목별 수급의 정답은 `m.stock.naver.com/api/stock/{code}/trend`.**

## 6. 마이그레이션 판단 — **폴백 완비**

따라서 순서는 이렇게 간다.

| 시점 | 할 일 |
|---|---|
| **지금** | ✅ 깨진 2건 수정 · ✅ 진단기(25항목)+기준선 · ✅ 위험종목/테마/뉴스/검색상위 폴백 이중화 |
| **주 1회** | `--compare` 실행으로 회귀 감시 |
| **기존 URL이 실제로 깨지면** | **폴백이 전부 자동으로 받는다. 수동 작업 없음.** |

수급까지 폴백이 붙으면서 **개편 당일 수동 개입이 필요한 지점은 사라졌다.**
남은 노출은 뉴스목록·종목별뉴스·시가총액 3곳인데, 모두 선정 로직이 아니라 표시·근거 계열이다.

## 7. 남은 숙제

- **프로그램 매매동향** — `/api/domestic/detail/{code}/` 하위에 program·programTrend·
  investor·pgtr 등 어떤 경로도 없다(전부 404). 그러나 **네이버에서 찾을 필요가 없다.** 이 값은 이미 **KIS API**에서 온다
  (`inquire-price`, `tr_id=FHKST01010100`, 필드 `pgtr_ntby_qty` — omakase.py 약 1791행).
  네이버 개편과 무관하게 동작한다.
- **시황 뉴스목록 / 종목별 뉴스 / 시가총액** — JSON 대체재 미발견. 각각 뉴스 키워드,
  AI 리포트 근거, 시총 필터를 담당한다. 개편으로 죽으면 해당 기능이 비지만
  선정 로직을 멈추지는 않는다(시총은 `siseListJson`의 `mks` 필드로 대체 가능성 있음 — 미검증).
- **캐치올 함정** — `theme/{no}/stocklist` 도 없는 번호에 `200 []` 를 준다.
  어댑터는 건수로 판정하지만, 앞으로 이 계열 API를 추가할 때마다 같은 검증을 붙일 것.
- CSS 선택자 의존은 폴백이 없는 3곳(`.articleSubject a`, `.title a`, `#_market_sum`)에
  아직 남아 있다. 진단기가 감시한다.

## 7-2. 🚨 3차 조사에서 발견한 또 하나의 조용한 실패 — 종목별 뉴스

`hyeoks_analyst.py` 의 `get_target_stock_news()` 가 **Referer 없이** 호출하고 있었다.

```python
res = requests.get(url, headers={'User-Agent': 'Mozilla/5.0'}, ...)   # Referer 없음
```

Referer 가 빠지면 네이버는 200을 주되 **뉴스 목록이 통째로 빠진 6,390바이트 껍데기**를 돌려준다.
이 함수는 예외도 내지 않고 `"개별 뉴스 없음"` 을 반환하므로, **AI 리포트가 그동안 종목별 뉴스
없이 작성돼 왔다.** 실측 — 005930/008930/000660 세 종목 모두 `0건 → Referer 추가 시 3건`.

**진단기가 이걸 왜 못 잡았나** — 진단기 세션은 `Referer` 를 전역으로 붙인다. 그래서 같은 URL이
초록으로 나왔다. **엔드포인트가 살아있는 것과, 소비자 코드가 그걸 제대로 부르는 것은 다른 문제다.**
→ 대책으로 `종목뉴스(운영헤더)` 항목을 추가해 **소비자가 실제로 쓰는 헤더 그대로** 호출해 본다.
앞으로 다른 지점도 이 방식으로 늘려갈 것.

## 7-3. 자동 감시 (워크플로)

`.github/workflows/naver_healthcheck.yml` — **매주 월요일 10:00 KST** 자동 실행.

| 항목 | 값 |
|---|---|
| cron | `0 1 * * 1` (UTC) = 월 10:00 KST — 장중이라 엔드포인트가 '실사용' 상태 |
| 실행 | `hyeoks_naver_healthcheck.py --compare` (기준선 대비 회귀 탐지) |
| 락 그룹 | `hyeoks-healthcheck-lock` — 시트를 안 건드리므로 다른 워크플로와 분리 |
| 타임아웃 | 10분 |
| 결과 보관 | `result.txt` 를 아티팩트로 90일 |

**알림 정책 — 문제가 있을 때만 텔레그램.** 정상이면 조용하다(주간 알림 피로 방지).
실행 여부 자체는 Actions 탭 이력으로 확인한다.

발송 조건은 셋 중 하나라도 해당할 때다.
1. 종료코드 1 (치명적 파손)
2. 출력에 `❌` 가 있음 (중요·보통 파손 — 종료코드로는 안 드러난다)
3. 기준선 대비 `🔻 회귀` 가 있음

문제가 감지되면 잡도 실패 처리해 Actions 탭에 빨간 X 로 남긴다.

### ⚠️ 운영상 주의 2가지

1. **깃허브는 저장소가 60일간 활동이 없으면 스케줄 워크플로를 자동 비활성화한다.**
   커밋이 뜸해지는 시기가 오면 Actions 탭에서 재활성화하거나 아무 커밋이나 하나 넣어야 한다.
   (이 워크플로가 조용한 것과, 아예 안 도는 것을 구분하려면 가끔 Actions 탭을 볼 것.)
2. **기준선은 CI가 갱신하지 않는다.** 일부러 그렇게 뒀다 — 자동 갱신하면 깨진 상태를
   '새 정상'으로 흡수해버려 회귀 탐지가 무의미해진다. 의도적으로 이관한 뒤에는
   로컬에서 `--save-baseline` 을 돌리고 결과 파일을 커밋할 것.

## 8. 개편 당일 체크리스트

```bash
python hyeoks_naver_healthcheck.py --compare
```

1. **치명적 항목이 초록이면 손댈 것 없다.** 폴백은 자동으로 동작한다.
2. `외국인·기관 수급 HTML` 이 빨간색이어도 → **조치 불필요.** `수급 JSON(폴백)` 이 초록이면
   omakase가 자동으로 그쪽을 탄다(값이 동일해 V2 점수도 그대로).
3. `위험종목 3종 HTML` 만 빨간색이면 → 조치 불필요. 수집기가 JSON 단독으로 명단을 만들고
   텔레그램으로 알린다(실측 270종목 확보).
4. 텔레그램에 `🚨 [위험종목 게이트 이상]` 이 오면 → 게이트가 실제로 비었다는 뜻이므로 즉시 확인.
