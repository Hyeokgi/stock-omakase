## 1. 지적 네 가지 — 전부 제 코드에서 확인했습니다

받아 적지 않고 `hyeoks_account.py`(구버전)에서 직접 확인했습니다. **전부 사실입니다.**

| # | 지적 | 확인된 코드 |
|---|---|---|
| ① | 순알파 합을 계좌 수익률로 표시 | `marks[d] = s - i - cost` → 지수를 뺀 값으로 곡선을 만들고 `account_return_pct` 로 명명 |
| ② | 장기 미청산을 마지막 마크에서 조기 청산 | `close_date = add_trading_days(entry, min(h, max(marks)))` |
| ③ | 잘못된 MDD 분모 | `denom = peak_open` — 전 구간을 봐야 아는 값(예지 편향) |
| ④ | 미청산·알파 부호를 승률로 표시 | `sum(1 for p in positions if p["final"] > 0) / len(positions)` |

①이 가장 큽니다. **시장이 −10%일 때 종목이 −8%면 알파는 +2%지만 계좌는 −8%입니다.**
보고했던 `+6.58%`는 실제로 `누적알파 217.07 ÷ 최대동시보유 33`이었고,
`MDD 4.55%`도 알파 곡선의 낙폭이지 계좌 낙폭이 아닙니다.
**계좌 숫자로 인용할 수 없다는 판단에 동의하며, 정정 경고를 그대로 유지합니다.**

## 2. 새 코드를 제가 확인한 범위

| 검사 | 결과 |
|---|---|
| `tests/test_account_nav.py` + `test_account_storage.py` | **47개 통과** |
| `hyeoks_verdict.py --self-test` | 88개 통과 |
| `test_tajeom.py` | 40개 통과 |

`simulate()` 를 직접 읽고 다음을 확인했습니다.

- NAV = `cash + qty × 동시점 가격` — 지수 차감 없음
- 매수 루프(시가)가 매도 루프(종가)보다 **앞**에 있어 당일 매도금이 당일 매수에 안 쓰임
- `peak, mdd, trough = initial_cash, 0.0, None` — MDD 기준점이 **초기자본**, 예지 편향 없음
- 정수 주식(`math.floor`), 현금 부족 거절, 양방향 수수료, 비중 상한은 **신규 매수만** 제약
- 청산일 거래정지면 열린 채로 유지

**특히 이것이 좋습니다** — 매일 `NAV − 초기자본 == 실현 + 미실현` 불변식을 검사하고
어긋나면 `InputError` 로 중단합니다. 제 구현에는 이런 자기정합성 검사가 **아예 없었고**,
있었다면 ①을 스스로 잡았을 것입니다.

⚠️ **네트워크·실데이터 경로는 확인하지 못했습니다.** `account_drive.py` 는 모의 응답
테스트만 봤고, 실제 Drive 연동과 386행 재계산은 실행하지 않았습니다.

## 3. 🆕 새로 발견한 문제 — 연구가 둘이 되면 채택 경로도 둘이 됩니다

`테마대장_종베_연구안_v1.md` 를 §6-12-3(9/8 확정 명세)과 대조했습니다.

**직접 모순은 없습니다.** 문서가 첫 줄에서 *"기존 §6-12 전체 유니버스 Q5 연구와
다른 탐색 연구"* 라고 선을 그었고, 주 분석·체결가 가정을 건드리지 않습니다.
*"스냅샷 현재가 매수 가정이면 15시대 매수 연구이지 실제 종가 체결 검증이 아니다"* 는
§6-12-3 이 적어 둔 한계를 더 날카롭게 표현한 것이라 그대로 수용합니다.

**그런데 세 가지가 남습니다.**

### ① 검정 family 가 정의되지 않았습니다

§6-12-3 은 *"주 분석 단 하나 — 이것만 채택 판단에 쓴다"* 로 못박았습니다.
새 문서는 *"기존 Q5 연구의 주검정·HAC·부트스트랩 기준을 자동으로 복사하지 않는다"* 고
했는데, **통계량 선택으로는 옳습니다** — 다른 질문에는 다른 검정이 맞습니다.

문제는 그것이 **family 를 정의하지 않은 채** 남는다는 점입니다. 두 연구가 각각
α=.05 를 쓰고 **어느 쪽이든 성공하면 채택**이 되면 실질 오류율은 두 배가 됩니다.
§3-5 가 확증 검정에 Holm 을 요구하는데 새 연구는 그 family 밖에 있습니다.

### ② 두 연구가 같은 날들을 봅니다

둘 다 8/28 이후 같은 15:05 스냅샷을 씁니다. §6-12-3 파일럿(20거래일)과 새 연구의
B·C 구간이 **같은 날**입니다. 새 문서가 *"확정 조건은 이후 미사용 날짜에서 검증한다"* 고
적은 것은 맞지만, **두 연구가 미사용 구간을 나눠 쓸지 겹쳐 쓸지**가 없습니다.
겹치면 재현이 재현이 아니게 됩니다.

### ③ 10/5 에 일이 셋으로 늘었습니다

🔒 강제조항(수급TOP2 폐기 vs `SUPPLY_V2_BAND`) + §6-12-3 파일럿 점검 +
새 문서의 *"10/5 는 초기 자료·가설 점검 시점 후보"*.
**일이 많아지면 '점검'이 '판정'으로 미끄러집니다.** 9/7 에 이미 겪었습니다.

### 조치 — 로드맵 §6-12-4 신설

| 항목 | 확정 |
|---|---|
| 확증 검정 | **§6-12-3 의 Q5 하나뿐.** 채택 판단은 이것으로만 |
| 새 연구의 지위 | **탐색적.** §3-5 대로 독립 재현 전 채택 금지 |
| 구간 | §6-12-3 의 파일럿·본·재현을 **먼저 소진**, 탐색 연구 확인 구간은 그 뒤 미사용 날짜 |
| 같은 날 공유 | 기술 통계까지만. **어느 쪽의 채택 근거로도 쓰지 않음** |
| 10/5 | **§3-2-2 강제조항만** 필수. 종가베팅은 자료 점검만, 판정 없음 |

**A/B/C 분해는 가져왔습니다.** `B−A = 대장 선정 효과`, `C−B = 추가 선별 효과`로
층을 나눠 재는 것은 4차 검토의 *"성과가 좋아도 무엇 덕분인지 모르면 유지도 개선도
못 한다"* 에 대한 직접적인 답이고, §4-5 의 A1·A2 와 같은 정신이라 이 프로젝트의
기본 태도로 삼았습니다. **B 에 하락 후보를 포함한다**는 조건도 §6-12-4 에 다시 적었습니다.

## 4. 고정 입력을 만들 수 있는가 — 재료 실사

`account-input-v2` 의 필수 키를 실제로 채울 수 있는지 확인했습니다.

| 키 | 상태 | 근거 |
|---|---|---|
| `rows` | ✅ | 시트에서 읽음(현재 386행) |
| `sessions` | ✅ | `hyeoks_snapshot_watch.py:67 trading_days()` — **지수 일봉에서 실제 거래일**을 받아 공휴일·임시휴장 자동 반영. 그동안 다른 모듈이 쓰던 평일 근사를 대체 가능 |
| `prices` | ✅ (작업 필요) | `hyeoks_phase2_exit.py:121 get_daily_bars()` 재사용. 원장 고유 종목 × 구간만큼 조회 |
| `theme_map` | ⚠️ **불완전** | 아래 참조 |
| `indices` | ✅ | 같은 일봉 경로 |

### 🚨 `theme_map` 이 요구 수준을 못 맞춥니다 — 질문 드립니다

명세는 *"신호 당시의 **모든** 소속 테마 ID"* 를 요구합니다. 우리가 가진 것은:

1. **원장 `주도테마` 열** — 신호 시점 값이라 시점 정확성은 맞지만 **종목당 대표 테마 하나**뿐입니다.
2. **테마 스냅샷** (`data/market_snapshot/*_theme.csv.gz`, **8/28 이후 16개 파일**) —
   구조가 **테마 → 상위 N 종목**(`topByChangeRate` / `topByTradingValue` / `topByMarketCap`)이라
   역매핑해도 **상위 종목만** 나옵니다. 완전한 소속이 아니고, 상승·거래대금 상위로 **편향**됩니다.
3. 원장 최소 진입일은 **2026-08-10** 이라 8/28 이전 구간은 스냅샷조차 없습니다.

즉 한 종목이 실제로 3개 테마에 속해도 1개로만 잡히므로 **`max_theme_weight` 상한이
느슨하게 걸리고, 테마 집중도가 과소평가**됩니다. 명세의
*"소속 없는 종목은 명시적인 개별 분류 ID 사용"* 은 **소속이 아예 없는 경우**를 다루지만,
**부분 소속만 아는 경우**는 다루지 않습니다.

**Q1.** 이 상태에서 어떻게 하는 것이 맞습니까?
  (a) 대표 테마 1개로 진행하되 **"테마 상한은 하한만 구속한다"**를 결과에 명시
  (b) 부분 소속을 **입력 오류로 보고 중단** — 완전한 소속 자료를 구하기 전엔 계좌 산출 안 함
  (c) 다른 방법

**Q2.** `price_basis` 가 `consistent_adjusted_ohlc` 만 허용하는데, 네이버 일봉의
조정 기준을 저희가 **검증할 수단이 없습니다**. 출처 문자열만 적는 것으로 충분한지,
아니면 분할·배당 이벤트를 별도로 대조해야 하는지 판단을 구합니다.
