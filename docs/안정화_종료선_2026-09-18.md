## 1. 왜 종료선이 필요한가

이번 주 실제로 일어난 일:

```
오류 발견 → 수정 → 검사도구 추가 → 그 도구가 또 오류 발견 → 수정 → 도구 추가 …
```

9/18 하루에만 A~E 다섯 건과 GPT P0 네 건을 고쳤고, 시험이 390 → 484건으로 늘었다.
고칠 때마다 나온 것이 실재하는 결함이었으므로 그 자체는 옳았다. 문제는 **끝을 정하지
않으면 이 루프가 스스로 멈추지 않는다**는 것이다. 그동안 본래 목적 —
**수익에 기여하는 선정 조건을 찾는 것**(운영대전제 §1) — 은 계속 뒤로 밀린다.

그래서 선을 긋는다. 다만 **선언이 아니라 기록으로** 긋는다.
"이제 안정된 것 같다" 는 증거가 아니다.

## 2. 종료 조건 (Production Stability Gate)

**실제 예정 실행 3회 연속**으로 아래 7개를 전부 만족하면 운영 감사 Phase 를 닫는다.

| # | 기준 | 증거 |
|---|---|---|
| ① | 핵심 CI 전부 green | `review_regressions.yml` 결과 |
| ② | DB_실적 schema contract 정상 | 실행 요약의 `schema=earnings-v2`, 범위오류 0 |
| ③ | DART primary 전체 대상 완료 **또는 명시적 결측** | 실행 요약의 `대상/성공/보유` |
| ④ | V1/V2/V3 조용한 파싱오류 0 | `[V3 INPUT]` 의 해석불가·범위밖 |
| ⑤ | feature_store / rank_pool 정상 기록 | 커밋된 파일과 행 수 |
| ⑥ | 백테스트 원장 정상 적재 | `append_rows` 성공 로그 |
| ⑦ | 핵심 workflow 에 설명되지 않은 실패 없음 | Actions 결과 |

### 이 문턱이 뜻하지 않는 것

- **"버그가 0" 이라는 뜻이 아니다.**
- 뜻하는 것은 하나다 — **"수익 연구를 재개해도 입력을 믿을 수 있다."**

### 느슨해지지 않게 코드가 막는 것

`stability_gate.py` 가 강제한다.

- **증거가 없으면 통과가 아니다.** 키가 빠지거나 `None` 이면 `EvidenceMissing` 이다.
  "확인 못 했다" 를 "괜찮다" 로 바꾸는 순간 이 문턱은 의미가 없다.
- `True` 만 통과다. `"Y"` 나 `1` 은 통과가 아니다.
- **한 번 떨어지면 연속 카운트가 0 으로 돌아간다.** "거의 3회" 는 3회가 아니다.
- **같은 `run_id` 를 두 번 세지 않는다.** 한 실행을 세 번 기록해 통과하는 길을 막는다.
- 기록은 `data/stability_gate/runs.csv` 에 **append-only**. 기준 7개가 행마다 남아
  나중에 "어느 기준이 떨어졌나" 를 다시 물을 수 있다.

```bash
python stability_gate.py            # 현재 상태
python stability_gate.py --self-test
```

## 4. 정정 — 7번은 이미 되어 있다

GPT 가 "최우선"으로 올린 **Feature Store 후보 전체 적재는 9/17 부터 이미 돌고 있다.**
실측:

```
data/feature_store/2026-09-18.csv.gz
  718행 × 50열   (그날 스캔한 전 종목)
  in_candidate_pool  Y=18 / N=700
  picked_by          차트TOP2=2 · 랜덤2=2 · 랜덤2_배지=2 · 나머지 공란
  store_version      feature-store-v1
  code_sha · run_id · captured_at 포함
```

GPT 가 적은 희망 목록과 대조하면 이미 들어 있는 것: `V1 V2 RS theme_rank
theme_hist_max price ma5 ma20 disparity dist_high high_60d high_250d market_cap
program supply_status vol_ratio seed_tag tajeom ai_brief market_type is_junk
kospi_rate warning_market index_above_ma5 in_candidate_pool gate_passed
picked_by code_sha run_id`.

**빠진 것은 셋뿐이다.**

```
v3_score                  ← 이번 V3 사고로 오히려 더 중요해졌다
policy_id                 ← rank_pool 에는 있는데 feature_store 에는 없다
earnings_schema_version / 실적 데이터 age
```

즉 남은 일은 **새 저장소 구축이 아니라 세 필드 추가**다. 다음 작업으로 올린다.

## 5. 입력 버전 기록 — 지금까지 한 것

GPT §6 의 취지("3개월 뒤에 성과가 달라도 전략 때문인지 입력 버전 때문인지 구분")를 받는다.

| 항목 | 상태 |
|---|---|
| `code_sha` · `run_id` · `captured_at` | ✅ feature_store · rank_pool · scanner_census |
| `policy_id` | ✅ rank_pool · scanner_census / ⬜ feature_store |
| `store_version` (`feature-store-v1`) | ✅ |
| `EARNINGS_SCHEMA_VERSION` (`earnings-v2`) | ✅ 이번 커밋 — 실행 요약에 찍힌다 |
| 실적 데이터 age (`갱신일시` 최저/최고) | ✅ 실행 요약에 찍힌다 / ⬜ 연구행에는 아직 |
| `latest_quarter` 를 소비자에게 전달 | ⬜ |

**파이프라인 버전 경계** (성과 비교 시 이 선을 표시한다):


## 6. V3 과거 데이터 취급 — 완전 복원을 시도하지 않는다

GPT §3 의 경고를 받는다. V3 버그 **시작일도 모르는 상태**에서 옛 픽을 완벽히
재구성하려 들면 다시 "검증을 위한 검증" 루프다.

원칙:

- 과거 행을 **소급 수정하지 않는다**(운영대전제 §5).
- `hyeoks_v3_probe.py` 는 **오늘 시트 기준 사고범위만** 계측한다.
  확정 영향 / 잠재 영향 / 영향 없음 / **재구성 불가** 로 나눈다.
- 과거 구간은 코호트로 표시하고 **공식 확증에서 분리**한다.

```
V3_INPUT_SCHEMA_BUG   ~2026-09-18   소비자가 row[8](영업이익증감률 QoQ)을 V3 로 읽던 구간
```

- **완벽한 역사 재건보다 깨끗한 새 표본을 빨리 시작하는 것이 더 가치 있다.**

## 7. 종료선 통과 후 — 알파 연구 복귀

종료선을 통과하면 이 문서의 역할은 끝나고 `docs/사전등록_2026-09-17_트랙R_조합탐색.md`
로 돌아간다. 이때 지켜야 할 것(이미 사전등록된 것이므로 여기서 바꾸지 않는다):

- 관측 단위는 **거래일**이다. 하루 50종목이 독립 표본 50개가 아니다.
- 탐색 30거래일 → 격리 10거래일 → 확증 30거래일, **단 1회**.
- 시도 상한은 코드가 막는다(`research_trials.py`, 단계 15/45/20 · 총 80).
- 중단 규칙: 하루 후보 풀 중앙값 < 10 이면 Rank IC 계획을 중단하고 설계를 다시 짠다.
- Track C 를 건드리지 않는다. Track R 통과는 채택이 아니다.

GPT 가 제시한 일정 감각(깨끗한 수집 시작 후 약 50~60거래일이면 첫 OOS 답)은
사전등록의 30+10+30 구간과 같은 크기다. **다만 이것은 작업 일정이지
수익성 입증 약속이 아니다**(진행계획 v2 서두).
