## 1. 왜 종료선이 필요한가

이번 주 실제로 일어난 일:

```
오류 발견 → 수정 → 검사도구 추가 → 그 도구가 또 오류 발견 → 수정 → 도구 추가 …
```

9/18 하루에만 A~E 다섯 건과 GPT P0 네 건을 고쳤고, 시험이 390 → 484건으로 늘었다.
고칠 때마다 나온 것이 실재하는 결함이었으므로 그 자체는 옳았다. 문제는 **끝을 정하지
않으면 이 루프가 스스로 멈추지 않는다**는 것이다. 그동안 본래 목적 —
**수익에 기여하는 선정 조건을 찾는 것**(운영대전제 §1) — 은 계속 뒤로 밀린다.

그래서 선을 긋는다. 다만 **선언이 아니라 기록으로** 긋는다.
"이제 안정된 것 같다" 는 증거가 아니다.

## 2. 종료 조건 (Production Stability Gate)

**KRX 거래일 end-to-end 생산 사이클 3회 연속**으로 아래 7개를 전부 만족하면
운영 감사 Phase 를 닫는다.

### 2-1. "1회" 의 정의 — 개별 workflow run 이 아니다

스캐너는 하루 144회 돈다. run 단위로 세면 **하루에 문턱을 통과**할 수 있다.
그래서 세는 단위는 **거래일**이다.

| 상황 | 판정 | streak |
|---|---|---|
| 거래일 · 7개 전부 충족 | `PASS` | +1 |
| 거래일 · 하나라도 미달 | `FAIL` | **0 으로 초기화** |
| 비거래일(주말·휴장) | `SKIP` | **늘리지도 끊지도 않는다** |

같은 `cycle_date` 는 두 번 기록되지 않는다.

### 2-2. 같은 파이프라인이어야 한다 — `stability_fingerprint`

3회가 서로 다른 코드에서 나온 기록이면 "연속" 이 아니다.
핵심 코드·워크플로·스키마 13개 파일의 SHA-256 앞 12자리를 지문으로 쓴다.

```
omakase.py · hyeoks_analyst.py · hyeoks_earnings_collector.py · earnings_schema.py
feature_store.py · rank_pool.py · scanner_census.py · hyeoks_tajeom.py · stability_gate.py
main.yml · earnings_collector.yml · consensus_aux.yml · ai_report.yml
```

**지문이 바뀌면 streak 는 0 으로 돌아간다.** 없는 파일도 지문에 반영된다 —
파일이 사라진 것도 변경이다. 따라서 **선행 수정 11건과 핵심 silent-exception
정리를 마친 뒤의 지문부터** 3회를 센다.

### 2-3. 기준 7개

| # | 기준 | 증거(기계) |
|---|---|---|
| ① | `ci_green` | `review_regressions.yml` 최신 결과 |
| ② | `earnings_schema_ok` | `schema=earnings-v2` · 범위오류 0 |
| ③ | `dart_complete` | 대상 = 성공 + **명시적** 결측 |
| ④ | `no_silent_parse_error` | **V1·V2·V3 각각의** telemetry (V3 만으로 True 로 만들지 않는다) |
| ⑤ | `store_written` | feature_store·rank_pool 의 날짜·run_id·지문 일치 + 유효 행수 |
| ⑥ | `ledger_written` | 그날 기대한 trade_id 가 시트에 **실재**하는지 read-after-write |
| ⑦ | `no_unexplained_failure` | required production workflow 의 expected state 충족 여부 |

AUX(컨센서스) 상태는 기준이 아니라 **별도 열(`aux_state`)** 에 기록한다.
보조 자료의 실패가 주 산출물의 판정을 흐리지 않게 한다.

### 2-4. 느슨해지지 않게 코드가 막는 것

`stability_gate.py` 가 강제한다.

- **증거가 없으면 통과가 아니다.** 키가 빠지거나 `None` 이면 `EvidenceMissing`.
- `True` 만 통과다. `"Y"` 나 `1` 은 통과가 아니다.
- 한 번 떨어지면 연속이 **0** 이다. "거의 3회" 는 3회가 아니다.
- 같은 거래일을 두 번 세지 않는다.
- 지문이 다르면 거기서 끊는다.
- `data/stability_gate/runs.csv` 에 **append-only**. 기준 7개와 지문이 행마다 남는다.

```bash
python stability_gate.py            # 현재 상태
python stability_gate.py --self-test
```

### 2-5. ⚠️ 아직 없는 것 — Evidence Builder

지금 `stability_gate.py` 는 **판정 로직만** 있다. 증거를 사람이 넣는 형태는
안정화 증거로 인정되지 않는다(사용자 지시 ②). 실제 CI·DART·V1/V2/V3·
feature_store·rank_pool·원장·workflow 상태에서 evidence 를 **기계적으로**
만드는 배선이 붙기 전까지 이 문턱은 가동되지 않는다.

## 6. V3 과거 데이터 취급 — 완전 복원을 시도하지 않는다

GPT §3 의 경고를 받는다. V3 버그 **시작일도 모르는 상태**에서 옛 픽을 완벽히
재구성하려 들면 다시 "검증을 위한 검증" 루프다.

원칙:

- 과거 행을 **소급 수정하지 않는다**(운영대전제 §5).
- `hyeoks_v3_probe.py` 는 **오늘 시트 기준 사고범위만** 계측한다.
  확정 영향 / 잠재 영향 / 영향 없음 / **재구성 불가** 로 나눈다.
- 과거 구간은 코호트로 표시하고 **공식 확증에서 분리**한다.

```
V3_INPUT_SCHEMA_BUG   ~2026-09-18   소비자가 row[8](영업이익증감률 QoQ)을 V3 로 읽던 구간
```

- **완벽한 역사 재건보다 깨끗한 새 표본을 빨리 시작하는 것이 더 가치 있다.**

- 관측 단위는 **거래일**이다. 하루 50종목이 독립 표본 50개가 아니다.

- 시도 상한은 코드가 막는다(`research_trials.py`, 단계 15/45/20 · 총 80).

GPT 가 제시한 일정 감각(깨끗한 수집 시작 후 약 50~60거래일이면 첫 OOS 답)은
