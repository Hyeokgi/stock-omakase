# 🔀 선정 정책 스위치 변경 체크리스트

작성 2026-09-14 (Claude) · 제안 ChatGPT · 대상: `ENVELOPE_BAND` · `SUPPLY_V2_BAND`
근거: 전략로드맵 §3-2 · §3-2-1 · §3-2-2 · §3-5-6, 운영대전제 §5

> **이 문서는 스위치를 켜라는 문서가 아니다.** 현재 둘 다 **OFF** 이고 이 문서가
> 그 상태를 바꾸지 않는다. 켜는 결정은 §3-2-2 의 10/5 조항과 사용자 승인이 정한다.
> 여기 적는 것은 **켤 때 같이 하지 않으면 조용한 정책 변경이 되는 일**의 목록이다.

---

## 0. 왜 필요한가 — 지금 배선으로는 조용히 바뀐다

```python
hyeoks_tajeom.py:25   POLICY_ID    = "oversold-veto-v2"
hyeoks_tajeom.py:26   POLICY_SINCE = "2026-09-07"
```

**하드코딩된 상수다.** `main.yml` 에 `ENVELOPE_BAND: "on"` 을 넣어도 이 둘은 안 움직인다.
그러면 스위치 이후의 행도 계속 `oversold-veto-v2 / since 2026-09-07` 로 표시되고,
§3-5-6 문제 4 의 "블록 안에서 `POLICY_SINCE` 가 움직이면 그 블록 무효" 라는
안전장치가 **영원히 발동하지 않는다.**

§3-2-1 은 *"ON 그날 이후 행은 별도 구간으로 분리 집계 — ON 전/후를 절대 합치지 않는다"*
를 요구한다. 그 요구를 지키려면 아래를 **한 묶음으로** 처리해야 한다.

---

## 1. 묶어야 하는 네 가지 (ChatGPT 지적)

`POLICY_SINCE` 날짜 하나를 고치는 것으로는 부족하다.

| # | 묶을 것 | 지금 상태 |
|---|---|---|
| 1 | **실제 적용된 설정과 코드 버전** | `data/scanner_census/envelope_census.csv` 의 `band_mode`·`band_pct`·`code_sha` 가 관측마다 기록한다 ✅ |
| 2 | **배포 시각과 처음 적용된 스캔** | 같은 파일의 `captured_at`·`run_id` 로 특정 실행을 지목할 수 있다 ✅ |
| 3 | **그 스캔에서 나온 후보·추천의 정책 ID** | 스캐너 쪽은 `policy_id`·`policy_since` 를 기록하지만, **원장 행별 연결 검증은 아직 안 됐다** ❌ |
| 4 | **구정책·신정책 표본의 분리** | 규칙은 §3-5-6 에 있으나 **행별 policy_id ↔ freeze 연결 검증 전까지 근사**다 ❌ |

3·4 는 v2 진행계획이 이미 미해결로 적어 둔 항목이다 —
*"정책일: 신호일 경계는 여전히 임시 분류. 행별 freeze/policy_id 와 연결 검증 전 확정 인증 금지."*

---

## 2. 🚫 하지 말아야 할 추론 — 내가 했던 비약

> ❌ *"`POLICY_SINCE` 를 10/5 로 적으면 재현 블록 A(10/06~11/06)가 유효해진다."*

**틀렸다.** 문서의 경계 규칙과 실제 표본이 돈 정책은 다른 것이다.

- 상수를 10/5 로 적었다고 해서 10/6~11/6 표본이 전부 신정책에서 나왔다는 **인증이 되지 않는다.**
  배포 시각·첫 적용 스캔·그 스캔의 산출물을 실제로 대조해야 안다.
- 반대로 10/6 첫 관측 **이전에** 적용됐다는 사실만으로 그 블록이 자동으로
  **혼합 블록이 되는 것도 아니다.** 그것도 표본을 봐야 안다.

→ **문서의 경계 규칙은 명확히 하되, 판단은 "실제 표본에 적용된 정책"을 기준으로 한다.**
날짜 상수는 그 검증의 **입력**이지 결론이 아니다.

## 3. 켤 때 순서 (제안 — 승인 전 실행 금지)

1. **켜기 전 기준선이 며칠 쌓였는지 확인한다.** `envelope_census.csv` 의 `band_mode=off`
   행 수와 `scanner_census.gaps()` 의 결측일.
   ⚠️ **"며칠이면 충분하다"는 근거는 없다.** 운영 진단에는 쓸 수 있지만
   정책 효과 비교의 검정력은 별도 계산이 필요하다. 여기서 단정하지 않는다.
2. `POLICY_ID` 를 새 값으로, `POLICY_SINCE` 를 적용 예정일로 올린다.
   **스위치 env 추가와 같은 커밋**에 넣는다. 따로 하면 그 사이 실행이 미분류로 남는다.
3. `.github/workflows/main.yml` 의 `파이썬 실행!` 스텝 `env:` 에 `ENVELOPE_BAND: "on"` 추가.
4. 배포 후 **첫 적용 스캔의 `run_id` 를 기록**한다. 인구조사 행이 자동으로 남긴다.
5. 그 실행의 후보·추천이 새 `policy_id` 로 원장에 들어갔는지 **실제로 대조**한다.
   여기까지 해야 3·4 가 근사에서 검증으로 바뀐다.
6. §3-2-1 의 **"ON 일자 기록"** 칸을 채운다.

되돌리는 조건도 §3-2-1 에 이미 있다 — *"ON 후 4주에도 과매도 표본이 N<10 이면
문턱 완화로도 안 되는 것이다 → 중기 채널 통합 또는 적재 중단. **문턱을 더 낮추지 않는다.**"*

---

## 4. 10/5 조항을 정확히 읽는다

§3-2-2 의 🔒 강제 조항은 셋 중 하나를 실행하라고 하지만 **예외가 붙어 있다.**

> 10/5 에 새로운 근거가 나와서 미루고 싶어지면, **그 근거가 무엇인지 먼저 여기 적고**
> 그 다음에 미룬다. 근거 없이 미루는 것은 이 문서가 막으려는 행동이다.

즉 *"어떤 상황에서도 반드시 켠다"* 가 아니다. **근거를 먼저 적으면 연기할 수 있다.**
막는 것은 연기 자체가 아니라 **근거 없는 연기**다. 이 구별을 흐리면 조항이 다른 규칙이 된다.

그리고 **2026-10-05 는 개천절 대체휴장**이다(`data/market_snapshot/nontrading.txt`).
v2 진행계획대로 그날은 *"확보된 마지막 거래일까지의 데이터로 점검"* 하며
새 시세나 새 픽을 요구하지 않는다.
